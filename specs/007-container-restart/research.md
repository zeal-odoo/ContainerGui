# Research: 容器重启

## Decision 1: 在单一操作中组合正常停止与启动

**Decision**: 由现有容器控制服务在同一异步操作中依次调用 `stopContainer` 与 `startContainer`。

**Rationale**: 当前机器上的 Apple `container` CLI 1.3.1 没有 `restart` 子命令；现有两个方法已使用精确标识、正常停止参数、非零退出处理和每阶段状态回读。组合它们是最小且可测试的实现。

**Alternatives considered**:

- 调用不存在的 `container restart` 插件：当前 CLI 明确报告插件不存在，不能作为兼容基线。
- 通过 shell 拼接 `stop && start`：违反参数数组和可替换命令边界，也无法在两个阶段间做状态判断。
- 在浏览器连续提交停止和启动：页面刷新、断线和重复点击会破坏单一操作与目标互斥。

## Decision 2: 重启仅接受运行中容器

**Decision**: 提交时重新读取目标状态，只有运行中才能创建重启操作；停止或已创建状态继续使用现有启动操作。

**Rationale**: 这保留“重启 = 运行中 → 停止 → 运行中”的明确语义，避免把外部状态变化悄悄降级为启动。

**Alternatives considered**:

- 对停止容器执行启动：会掩盖过期页面状态，与规格中的冲突处理不一致。
- 所有状态都显示重启：增加无效操作和解释成本。

## Decision 3: 复用确认、幂等和目标锁

**Decision**: 新接口要求精确 `confirmationTarget` 和 UUID 幂等键，并使用现有容器目标锁。

**Rationale**: 重启会造成服务中断；复用已验证边界可以阻止刷新重复提交、同目标并发启动/停止/删除和错误目标操作。

**Alternatives considered**:

- 无确认的一键重启：交互更少，但无法充分展示中断目标。
- 新建独立锁：会让同一容器上的重启与现有控制操作并行，产生竞态。

## Decision 4: 最终运行状态是唯一成功判定

**Decision**: 停止结果必须为停止状态才进入启动；启动结果必须为运行状态才完成操作。失败时保存可获得的实际状态回读，无法回读时使用现有安全错误映射。

**Rationale**: 两个命令退出零仍可能未改变状态，且启动失败时容器可能留在停止状态。最终回读能够避免虚假成功。

**Alternatives considered**:

- 只检查两个退出码：与宪章的状态回读要求冲突。
- 停止失败后仍尝试启动：可能把未知状态变为更难诊断的状态。

## Decision 5: 浏览器验证不触发真实重启

**Decision**: 自动化验证检查按钮可见性、确认文案和请求形状；后端顺序由 stub 控制器验证。真实环境只做 CLI 版本和只读状态回读。

**Rationale**: 用户当前运行 PostgreSQL、Odoo 和 Ubuntu 容器，自动化测试不得中断真实服务。

**Alternatives considered**:

- 点击真实重启按钮：会造成未单独授权的服务中断。
- 仅检查源文本：不能证明 API 顺序、失败短路和幂等行为。
