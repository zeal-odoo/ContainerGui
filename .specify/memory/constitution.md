# Container GUI Constitution

## Core Principles

### I. 官方 CLI 是唯一事实来源
所有容器、镜像、卷、网络和系统状态必须从当前机器上的官方 `container` CLI
读取。可使用短期内存缓存改善页面体验，但不得建立会与 CLI 状态分叉的影子数据库。
CLI 提供结构化输出时必须优先使用 JSON；每次变更后的成功判定必须包含一次独立状态回读。

理由：GUI 是官方 CLI 的轻量操作面，不是第二套容器运行时。避免双重状态可降低版本升级、
异常退出和外部 CLI 操作造成的数据不一致。

### II. 本机优先与安全变更
服务默认且仅允许绑定 `127.0.0.1`。MVP 不提供远程访问；在认证、授权和 TLS 另行设计并
验收前，不得开放局域网监听。后端只能执行显式允许的命令和参数，必须以参数数组启动进程，
不得拼接 shell 命令。删除、强制删除、批量停止和 prune 等破坏性操作必须展示解析后的目标，
由用户二次确认；操作完成后必须核对退出状态、标准错误和实际资源状态。

理由：本机管理工具仍可删除重要数据或暴露高权限能力，默认边界必须在实现上可验证，不能只
依赖界面提示。

### III. 测试先行和可替换命令适配器
每项行为变更必须先有失败测试，再进行最小实现并使测试通过。命令执行层必须通过协议或等价
边界可替换，使单元测试使用固定 JSON、标准输出、标准错误、退出码和超时样本，自动化测试
不得修改用户的真实容器状态。只读的真实 CLI 冒烟测试必须与模拟测试分开标记和执行。

理由：CLI 输出和失败模式是本项目最易变化的外部契约；测试夹具可以在不触碰用户运行环境的
前提下稳定复现兼容性问题。

### IV. 可独立验收的增量交付
每个用户故事必须形成可单独运行、可单独测试的纵向切片。首个切片只覆盖系统健康、容器列表、
详情、启动、停止和日志；镜像、卷、网络、创建容器、终端和构建能力必须在后续故事中逐步加入。
新增能力不得使已完成故事依赖未完成模块。

理由：工具的核心价值是快速替代高频 CLI 操作，先交付完整的小闭环比一次覆盖全部命令更容易
验证，也更符合轻量目标。

### V. 简洁、可观察、可兼容
实现必须保持单一 Swift 服务和静态浏览器界面，不得为当前需求增加数据库、前端构建链或分布式
组件。所有命令必须记录命令类型、目标、开始/结束时间、退出码和可安全展示的错误摘要，但不得
记录环境变量值、注册表凭据或用户输入的秘密。启动时必须探测 CLI 路径和版本；不支持的版本或
输出格式必须明确报错，不得静默猜测字段。

理由：依赖和隐藏状态越少，安装、诊断和升级越可靠；结构化审计信息能让用户区分“请求已发送”
与“目标状态已改变”。

## 技术与安全边界

- 基线运行环境为 Apple Silicon、macOS 26、Swift 6，以及本机已安装的 Apple `container` CLI；
  首个兼容基线为当前已验证的 CLI 1.3.1。
- B/S 架构中的 Swift 服务负责命令编排、解析、校验和状态回读；浏览器只能调用受控 HTTP API，
  不能提交任意可执行文件、子命令或原始 shell 文本。
- 初始技术路线为 Hummingbird 2、原生 HTML/CSS 和少量无构建步骤 JavaScript。持续日志优先使用
  Server-Sent Events；只有出现明确的双向交互需求时才引入 WebSocket。
- MVP 不直接链接 Apple Containerization 底层包，也不直接调用 `container` 的 XPC/内部 API。
  只有在官方稳定性、授权模型和版本兼容性得到单独验证后才可修改此边界。
- 所有资源标识必须来自最新列表或详情回读，并作为独立进程参数传递。批量操作必须逐项记录结果，
  不得把部分成功显示为整体成功。
- 页面必须支持中文界面、键盘操作、清晰的加载/空状态/失败状态，并保证危险操作不能由页面刷新
  或重试自动重复提交。

## 开发流程与质量门禁

1. 每项功能遵循 Spec Kit 的 specification -> clarification -> plan -> tasks -> implementation 流程；
   未解决的高影响需求歧义不得进入实现。
2. 规格必须给出可测的正常流程、空状态、CLI 未启动、超时、非零退出、输出无法解析、资源在操作前
   已变化等验收场景。
3. 代码合入前必须通过 `swift test`、命令适配器夹具测试、HTTP 契约测试和浏览器关键流程测试。
   真实环境测试默认只读；任何真实写操作均需单独、明确授权。
4. 对 CLI 结构化输出模型的每次修改，必须保留对应版本夹具并验证未知字段兼容、缺失必需字段失败、
   非 JSON 错误输出和取消/超时处理。
5. 完成声明必须同时包含：测试通过、浏览器可见结果、CLI 版本记录、变更后目标状态回读。进程退出码
   为零或页面显示成功均不能单独作为完成证据。
6. 超出当前用户故事的优化、抽象或重构必须留作后续任务，不得混入当前改动。

## Governance

本宪章优先于项目中的其他开发惯例。规格、计划、任务和代码评审必须逐项检查上述原则；任何例外
必须在计划的 Constitution Check 中写明原因、影响、替代方案和退出条件。宪章修订必须记录变更内容，
按语义化版本管理：删除或重新定义原则为 MAJOR，新增原则或实质扩大治理范围为 MINOR，措辞澄清为
PATCH。每次修订必须更新 Sync Impact Report 和日期。实现阶段发现与宪章冲突时必须停止并先修订规格、
计划或宪章，不能用代码事实反向默许违规。
